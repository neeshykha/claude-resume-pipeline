## scheduled-agent-detector
**URL:** https://github.com/neeshykha/scheduled-agent-detector
**What:** A nightly silent-failure detector for a fleet of scheduled AI agent tasks. The problem it solves is specific: an interactive agent session that hits a permission prompt waits for a human, but a *scheduled* run can't answer, so it skips the blocked call, exits 0, and reports "completed" while the one write that mattered never happened. A run that did the work and a run that was silently blocked are byte-identical in their own reports. So every task declares the artifact it should produce and on what schedule, and the detector judges it on file mtime against a cron-derived due time — six verdicts (OK / QUIET-OK / UNVERIFIABLE / MISSING / STALE / NOT-DUE), a failure signature on every miss from a catalog of nine real incident types, and md/JSON/HTML reports. Reading the scheduler's own task list lets it separate "didn't run" from "ran and didn't write." A coverage section names the scheduled tasks nobody is watching, and a lint pass finds blocked-command patterns in every task's instructions before they cause a failure. Standard library only, 57 tests, all on real files with forced mtimes.

The judgment worth citing is in what it refuses to say. A folder the process isn't allowed to read (macOS privacy protection turns a denial into an empty result) is reported UNVERIFIABLE and exits non-zero, never MISSING — a blind check that reports healthy is the exact failure the tool exists to prevent. Three unrelated tasks missing on the same night is read as a dispatch backlog and confirmed on the next pass, not three incidents. Replaying past nights marks in-place state files unverifiable, because their history genuinely was never recorded. And the first live run caught a bug in the detector itself: its grep for blocked shell patterns matched a task's instruction *warning against* that pattern, blaming the task for the thing it was being careful about. The fix reads only code, skips warnings, and falls back to "cause unknown, read the transcript" rather than naming a cause it can't support.
**Cite when:** JD asks about running AI in production after launch, AI operations or performance monitoring, reliability of automated/agentic workflows, observability, or "what do you check first when it's down." This is the direct answer to the ownership question in AI Operations and AI Performance roles (Devoted Health's "production ownership of a portfolio of LLM workflows") and to Solutions Engineer and **Forward Deployed Engineer** JDs asking for operational depth rather than prototypes — the failure stories are real incidents with real fixes, including a launchd job that died silently after an OS update and now pages when it can't start. Pairs with skill-regression-harness: that one tests whether the right agent fires, this one tests whether it did its job.
**Resume line:** Built a nightly silent-failure detector for a fleet of scheduled AI agents that verifies each run by artifact evidence rather than the run's own success report, catching blocked-permission failures that exit cleanly and badge "completed"; it classifies each failure against a catalog of recurring causes and reports which tasks it cannot vouch for.

## skill-regression-harness
**URL:** https://github.com/neeshykha/skill-regression-harness
**What:** A regression suite for AI agent skill definitions, which are prompt-matched rather than called — nothing imports them, nothing type-checks them, and nothing fails loudly when one stops working, so a model upgrade can silently stop a production skill from firing. Two layers: free static checks (frontmatter completeness, name/directory agreement, duplicate names, trigger phrases claimed by more than one skill, and every filesystem path a skill tells the agent to read), and live dispatch testing of 58 frozen prompts across sixteen confusable groups, twenty of which expect *no* skill to fire. Safety matters here because two of the skills reach live Salesforce and Gmail: dispatch runs under a tool denylist, so a skill loads and its routing decision is visible while nothing it reaches for executes. Recorded live run (2026-08-29, against the case set as it stood that day): 21/23 correct, 0 errored, across six skills. Scoring reuses claude-eval-kit, making skill dispatch its second domain.

The best story in this repo is that **the original safety mechanism was wrong and the harness caught it.** Dispatch first ran under `--allowedTools Skill`, assumed to be a restrictive allowlist. It is not — a probe confirmed Bash still executed under it, and an early write failed only because of an unrelated working-directory guard. The consequence was concrete: testing a skill whose own instructions say "run the harness" recursed, and 213 junk rows appeared in a predictions file. That anomaly is what exposed the false assumption. The first fix — plan mode — was itself reverted within the hour: it was genuinely safe, but it declines to dispatch side-effectful skills, so it silently changed what the harness measured (one case went 0/3 under it versus 2/3 without). A safety control that suppresses the behaviour under test is a broken harness, not a safe one. Final design is a tool denylist verified by the same probe that caught the original flaw, plus an environment-variable recursion guard so a nested run cannot start a dispatch layer even if tool gating breaks again.
**Cite when:** JD asks about AI governance, LLM reliability or evaluation in production, post-deployment monitoring, agent QA, regression testing of AI systems, or "how do you keep AI working after you ship it." This is the strongest answer to the AI-governance language now common in the funnel (Alston's "governance standards for responsible, secure, compliant AI use"; GitLab AI Transformation Owner's AI evaluation and piloting). It covers the half of AI ops that deflection-audit and claude-eval-kit do not: not whether the AI was right, but whether the system still routes to it at all. The safety design — testing skills that reach production systems without letting them touch those systems — is the talking point for anyone asking how you validate against live infrastructure without risk. Also unusually strong evidence of honest engineering: five defects were found in the harness itself by running it, including two consecutive wrong answers to the same safety question, one bug that was masking the suite's only real finding, and a case-design flaw the harness surfaced about its own scoring.
**Resume line:** Built a regression suite for AI agent skill definitions combining static validation with sandboxed live dispatch testing, catching silent routing failures that model upgrades introduce; found and fixed five defects in the harness itself, including a false safety assumption about tool isolation and one bug that was masking the suite's only genuine finding.

## deflection-audit
**URL:** https://github.com/neeshykha/deflection-audit
**What:** Audits the deflection rate an AI support deployment reports. Vendors count deflection as conversations the AI closed without a human handoff, which counts closures rather than resolutions — abandonment, re-contacts, and later escalations all look identical to a success. This re-judges every AI-closed conversation from the transcript alone (at close time, without seeing the follow-up signal), then recomputes the rate crediting only closures that hold up. On a 40-conversation labeled set: 80.0% claimed vs. 55.0% audited, a 25-point overstatement. Two layers by design — the auditor is scored against ground truth first (25/32 outcomes, 8/11 confusable-pattern traps) before its numbers are trusted. Ships a static HTML report, a reusable QA rubric, and 18 unit tests covering the deterministic half.
**Cite when:** JD asks about measuring AI deployment success, post-launch adoption or ROI, deflection/containment metrics, AI quality assurance, or "how do you know the AI is actually working." Especially strong for Deployment Strategist, AI Engagement/Enablement, and AI Operations roles — it answers the rollout-health question the other repos don't touch. Also the best evidence of metric skepticism applied to a number he personally owns (85% deflection via Maven AGI at iApts). Pairs with claude-eval-kit as proof that kit generalizes to a second domain.
**Resume line:** Built an audit tool measuring true vs. reported AI support deflection, finding a 25-point overstatement on a labeled conversation set by re-judging closures on whether the customer's problem was actually resolved.

## kb-health-checker
**URL:** https://github.com/neeshykha/kb-health-checker — live at https://neeshykha.github.io/kb-health-checker/
**What:** Paste a help-center article and get an AI-readiness grade: how well that article will hold up when a RAG copilot (Intercom Fin, Maven AGI, or anything similar) answers customer questions from it. The premise is that AI support agents don't read an article the way a human does; they retrieve a chunk and generate from whatever that chunk says on its own, so content that reads fine end-to-end still fails as source material. Five weighted categories — structure and chunkability (25%), answer clarity (25%), self-containment (20%), machine readability (15%), and language quality (15%) — score against checks like sections over 350 words, headings that open with "This setting also…", "click here" link text, screenshot-only steps, and div-soup markup. Every finding comes with why it matters for retrieval and a concrete fix, graded A (≥90) down to F (<55), with built-in good and bad example articles that demonstrate the rubric. One static HTML file: roughly 300 lines of vanilla JS on the browser's own DOMParser, no build step, no backend, no analytics, and nothing leaves the browser.
**Cite when:** JD asks about knowledge base or content operations, RAG and retrieval quality, AI copilot or chatbot deployment, support content strategy, or "what do you do when the AI gives a wrong answer." This is the cleanest demonstration of the SME-first-then-encode pattern in the whole set: every check in it is a failure mode he diagnosed in production while owning the AI copilot relationship for a support knowledge base, and the framing is explicitly that the root cause was the content, not the model. It's also the most recruiter-friendly link he has, since a reviewer can grade an article in about fifteen seconds with nothing installed. Pairs with deflection-audit: that one measures whether the AI's answers were right, this one diagnoses why they weren't.
**Resume line:** Built and shipped a browser-based AI-readiness grader for support knowledge bases, encoding production diagnostic experience into a five-category weighted rubric that scores help-center articles on how well they survive retrieval by a RAG copilot and returns a specific fix for every finding.

## claude-resume-pipeline
**URL:** https://github.com/neeshykha/claude-resume-pipeline
**What:** AI-powered resume tailoring and job discovery pipeline. CLAUDE.md encodes ATS optimization logic; Python handles ATS board polling (50+ companies), composite scoring, and PDF rendering. Also ships **`audit_scores.py`**, a calibration audit that re-derives the pipeline's own scores from the rubric that produced them. Because half the rubric is judgment (keyword overlap, reach penalties) and half is mechanical (title tier, source quality, company bonuses, salary band, freshness), it computes a *legal envelope* per job rather than a single right answer: a score outside its envelope is provably wrong, and a score inside it is reported with the judgment it would require, for a human to weigh. It also detects **rubric drift** — jobs scored under a retired version of the rules whose recorded tailoring tier the current rules would not grant. On 205 scored rows it found 15 still-queued roles carrying a location bonus a rule change had already retired, five of them sitting a full tier above where today's rubric puts them. The auditor is scored against hand-adjudicated cases (6/6) before its output is trusted.
**Cite when:** JD mentions AI tooling implementation, workflow automation, encoding domain expertise into AI systems, or — for the audit half — measurement discipline, scoring model governance, config drift, or QA of an automated decision system. The audit is the strongest part to cite for roles that care whether someone checks their own automation: it audits a scoring model he built and depends on, and it deliberately reports what it *cannot* prove rather than manufacturing certainty. Use carefully — citing the resume pipeline *in a resume it produced* can be a clever meta-point or too cute, judge per company culture.
**Resume line:** Designed an AI job-discovery and resume-tailoring pipeline encoding ATS screening logic into a Claude instruction layer, with automated polling of 50+ company job boards; added a calibration audit that re-derives every score from the rubric and flags decisions made under superseded scoring rules, surfacing 15 queued items whose tier no longer matched current criteria.

## piedmont-bloom-planner
**URL:** https://github.com/neeshykha/piedmont-bloom-planner — live at https://neeshykha.github.io/piedmont-bloom-planner/
**What:** A native-plant planting planner for the Georgia Piedmont that solves for continuous bloom rather than listing species. Takes bed dimensions, sun, soil moisture, soil texture, and a height cap; filters a 41-species database to what will actually grow there; and runs a greedy solver picking a set that keeps at least two species flowering every month from March through November. Computes quantities from mature spread against bed area. The design decision worth naming: it separates bloom gaps you can close (an eligible plant covers that month, just unselected) from gaps your constraints made impossible, and for the latter it names the binding constraint. Encodes real regional judgment — heavy clay is treated as a first-class constraint, and the tool warns at three severities that butterfly weed, the default monarch recommendation everywhere, crown-rots in wet Atlanta clay. Single self-contained HTML file, no dependencies, no network calls, runs from `file://`.
**Cite when:** ONLY where personal building, curiosity, or "what do you make for yourself" is genuinely relevant — startups, AI-native companies, product-minded teams, or an interview asking what he builds outside work. Its real strength is that a reviewer can click a link and use it in ten seconds with nothing installed, which no other repo in the set offers. **Do not cite it** for AI deployment, evaluation rigor, Python depth, or enterprise systems work; there is no AI component and no test suite. Never lead with it. Same narrow lane as Stride-App, but more polished and actually usable by a stranger.
**Resume line:** Built a browser-based native-plant planner that solves for unbroken seasonal bloom coverage, encoding regional soil and horticultural constraints into a dependency-free single-file tool.

## peptide-evidence
**URL:** https://github.com/neeshykha/peptide-evidence — live at https://neeshykha.github.io/peptide-evidence/
**What:** A structured evidence-grading system for research peptides, where each compound gets a standalone record graded under a fixed, frozen rubric with every claim traced to a primary source (PMID, NCT, DOI, or a named FDA document) and every gap stated outright. The rubric runs on three axes that are deliberately never averaged into one score: evidence level (L1–L5, systematic reviews of RCTs down to in-vitro and animal-only), indication match (does the evidence match the use, route, *and* dose actually being marketed), and source independence (independent replication versus single-sponsor or commercial-only literature). Where the grade differs between the indication studied and the indication marketed, both are reported, because a single number would hide the finding. The method rules are the substance: per-claim retrieval status (`retrieved`, `abstract-only`, or flagged as learned-from-summary and excluded from synthesis until upgraded), an enforced search order that puts registries and FDA documents before PubMed and vendor pages last and only for market facts, absence recorded as a result rather than skipped, withdrawn claims kept as visible inline corrections so an error can't silently reappear, and a mandatory counterbalance section covering unfavorable findings and what would move the grade in either direction. Records come out of an AI-assisted research pipeline running under a written protocol, with a separate adversarial audit pass in a clean context. Static self-contained HTML per record; 4 of 43 planned records published.
**Cite when:** JD asks about AI-assisted research workflows, evidence synthesis, structured grading or rubric design, provenance and citation discipline, or guardrails that keep a generative pipeline from inventing support for a claim. The transferable argument is process design under adversarial conditions: the retrieval-status field, the enforced source hierarchy, the clean-context audit pass, and the refusal to collapse three axes into one number are all the same instinct as the "never trust a task's own report" rule in scheduled-agent-detector. Health and life-sciences companies are the obvious fit. **Judge the audience first** — the subject matter is research peptides, which reads as a personal-interest domain and won't land everywhere, so cite the method rather than the compounds, and skip it for conservative enterprise audiences.
**Resume line:** Designed an evidence-grading system for a contested research literature, using a frozen three-axis rubric, per-claim provenance with explicit retrieval status, and an enforced source hierarchy, run through an AI-assisted pipeline with a separate adversarial audit pass in a clean context.
