# Job Search Dashboard: handoff from the Steward session (2026-09-19)

Written by Claude at the end of a session that built the Steward home-maintenance app. Aneesh
wants a dashboard for the daily job pipeline and chose to build it in a fresh session here.
Nothing in this repo was changed; this file is the only thing that session wrote.

## The decision

Build a **read-only HTML dashboard**, regenerated by the daily pipeline, that lands in HTML Shelf.
It combines the three lists where Aneesh is the bottleneck, not the pipeline:

1. **Jobs to apply to**
2. **Manual checks**: career sites the pipeline can't scrape, which he has to open by hand
3. **Interviews**: upcoming rounds, prep status, missing post-mortems

He picked this scope: **build jobs + manual checks now, add interviews after.**

## Why it's shaped this way

Steward works as an editable app because the user types the data in, so the browser can own it.
The job pipeline is the reverse: a scheduled task produces the data into files here, and a Shelf
page can't read local files. So the dashboard is a generated report with the data baked in, the
same way other automation reports reach the Shelf. It is not an app that owns data.

Write-back (marking a job applied from the dash) was considered and rejected for v1. It would be a
second source of truth next to `outcomes.csv`, and this repo's history with drift is the argument
against. Marking applied stays with the existing confirmation-email sync and `mark_applied.py`.
The dash shows state; it doesn't set it.

The one piece of state the dash does keep is personal and harmless: "I checked this site" ticks
on the manual list, stored in the Shelf's per-page storage via `localStorage`. The pipeline never
reads them, so they can't drift against anything.

  carry a URL or only a search `query`; if only a query, the generator needs a URL field added to

### Interviews: phase two, needs one new file
- No structured record of upcoming interviews exists. `outcomes.csv` has `furthest_stage`
  (`applied / assessment / interview / onsite / offer`) and buries dates in freeform `notes`.
- Prep and post-mortems are markdown: `interview_prep/[Company]/prep_round[N]_[type].md` and
  `postmortem_round[N]_[type].md`. Cross-company lessons roll up to `_lessons_learned.md`.
- Upcoming rounds are detected from calendar and Gmail by the `interview-scan` scheduled task and
  the `interview-loop` skill.
- Plan: have that scan write a small `interviews.json` (company, role, round, datetime, has prep
  file, has post-mortem). It's a cache of a scan, not a ledger, so it doesn't break the
  no-new-source-of-truth rule. The dash reads it and flags rounds with no prep and past rounds with
  no post-mortem.

## How to build it

- One **read-only generator script** in `pipeline/` (for example `build_dashboard.py`). Reads the
  CSV, the watchlist, the enrollment queue, and later `interviews.json`. Writes one HTML file. No
  schema changes, no hand edits, and it never calls `mark_applied.py`, `mark_outcome.py`, or
  `update_tracking.py`.
- Add it as a step in `pipeline/daily_task_prompt.md`, after tracking is updated (Step 6 or later).
  That file is the canonical routine; do not put steps in the scheduled-task `SKILL.md`.
- Respect the run rules from Step 0 of the daily prompt: no inline `python3 -c`, no shell loops or
  chained commands, named scripts only, temp scripts as `pipeline/_taskname.py`. A failed dashboard
  build must never fail the run; the digest email stays the primary output.
- Output: a stable filename (for example `job_dashboard.html`) written to `~/Downloads` so the
  Shelf's folder watcher picks it up. Keep a dated copy in `pipeline/jobs/` if history is useful.
- Self-contained HTML, vanilla JS, data embedded as a JSON literal. No build step. It's a report
  with a few checkboxes, not a React app. Match the voice rules in this repo's CLAUDE.md for any
  copy on the page.

## Verify first: this decides afternoon vs weekend

The manual-check ticks only survive if each day's regenerated file **updates the same Shelf page**.
If it imports as a new page, the ticks start empty every day.

- The Shelf's notes (`~/HTMLShelf/CLAUDE.md`) say per-page storage persists and that right-click
  **Update from Source** keeps a page's saved data. They also say filename variants like
  `name (1).html` import as new pages.
- Not checked: what the Downloads watcher does when the **identical filename** lands again. Read
  `Library.swift` and the mirror code for that path, and check `seen_sources.json` handling.
- If it doesn't update in place, options are: a small Shelf change to auto-update on same-source
  re-import, or a live-URL style entry pointing at a stable file. Note that live-URL entries get
  **no** storage bridge, so that route would need its own answer for the ticks.
- Never edit the Shelf's `library.json` while the app is running.

Key the ticks by something stable (company name or watchlist id), and store a date with each tick
so the page can show "checked 3 days ago" and let a tick go stale after a week.

## Suggested page layout

- Top tiles: ready to apply, expiring within 7 days, manual checks due, applied and quiet 10+ days.
  Interviews tile added in phase two.
- **Apply queue**: company, title (linked), fit score, coverage, unmet hard reqs, days left,
  tailored PDF path. Sorted by days left.
- **Manual checks**: company, why it's manual, last pipeline hit, careers link, tick with date.
  Unticked and stale first.
- **Gone quiet**: applied and pending, by age.
- Phase two, **Interviews**: upcoming with prep status, recent with post-mortem status.

## Patterns worth reusing from Steward

Files are in `/Users/aneesh/Documents/AI Projects/`: `steward.jsx`, `steward.html`, and the spec
`34-steward-home-maintenance.md`.

- Status-colored stat tiles that filter the list below them.
- Relative wording ("12 days overdue", "due in 3 wks") with the absolute date underneath.
- Dense rows, mono font for dates and numbers, CSS variables for a light and dark palette.
- `localStorage` wrapped in try/catch, with the page fully usable if storage fails.

Steward's React build and bundling recipe are **not** needed here. This page should be plain HTML.
